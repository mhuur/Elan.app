# Avel — Suivi sport

App PWA mobile-first de suivi sportif (running, vélo d'appartement, muscu, HIIT, étirements). UI en français, charte **« bord de mer » : ardoise & écume, sombre** (juillet 2026 — remplace le vert sauge/crème clair).

## Déploiement

**Un commit git ne publie RIEN.** La mise en ligne est une étape à part, à faire à chaque fin d'étape puisque l'utilisateur juge sur l'app en ligne :

```
npm run build
npx firebase-tools deploy --only hosting
```

⚠ **JAMAIS `--non-interactive` sur ce `deploy`.** Le drapeau supprime les demandes de confirmation et le classificateur de permissions de Claude Code **refuse la commande** quand il est présent. Relevé sur les transcripts du projet : les 5 déploiements sans le flag sont tous passés (29-30/07/2026), les 3 tentatives avec ont été refusées — d'où la journée du 09/08/2026 passée à croire, à tort, que la permission de déployer avait été retirée, alors que seule la commande avait changé. Diagnostic transposable : **avant de conclure qu'un droit a disparu, comparer la commande exacte à celle qui marchait**, les transcripts sont dans `~/.claude/projects/…-Elan/*.jsonl`. `publier-l-app.bat` (racine de `Sport/`) enchaîne les deux commandes pour l'utilisateur, sans le flag, et rappelle qu'il faut rouvrir la PWA **deux fois** pour dépasser le cache du service worker.

L'app vit sur **https://avel.web.app** — c'est l'URL à utiliser. Le projet Firebase garde son ID d'origine `routine-sport-ca440` (un ID de projet est **immuable**) : `avel` est un **second site Hosting** du même projet (`firebase hosting:sites:create avel`), et `firebase.json` déclare les deux sites sur le même `dist/`, si bien qu'un `npx firebase-tools deploy --only hosting` publie sur les deux. L'ancienne URL `routine-sport-ca440.web.app` reste donc valide (utile : c'est encore elle dans les PWA déjà installées).

Ce qui a dû suivre le nouveau domaine, à refaire pour toute nouvelle origine :
- `ALLOWED_ORIGINS` des **deux Workers** (`worker/strava-elan.js`, `worker/notif/notif-elan.js`) + `npx wrangler deploy` dans chaque dossier — sinon CORS bloqué sur la synchro Strava et l'abonnement aux rappels ;
- **domaines autorisés de Firebase Auth** (sinon `auth/unauthorized-domain` à la connexion Google) : ils ne suivent PAS automatiquement les sites Hosting additionnels. Ajout fait via l'API `identitytoolkit.googleapis.com/admin/v2/projects/{id}/config` (`authorizedDomains`) avec le jeton firebase-tools du configstore — même mécanisme que `scripts/fetch-logs.mjs`, à défaut console Firebase → Authentication → Settings.

Attention, **localStorage et abonnements push sont par origine** : sur un nouveau domaine, les réglages locaux (heures de rappel, ancre de la section plan, dernière synchro Strava) repartent à zéro et il faut se réabonner aux notifications. Les séances et logs, eux, sont dans Firestore : rien à migrer.

## Nom et identité

L'app s'appelait **Élan** (feuille verte) ; renommée **Avel** en juillet 2026 — breton pour « le vent ». Le **nom affiché reste Avel** ; seule l'identité visuelle a changé.

Logo (juillet 2026) : **l'ogive** — une amande verticale tendue aux deux pointes, écume dégradée sur ardoise. Un seul chemin dans un carré de 512 :
`M256 88 C 344 194, 344 318, 256 424 C 168 318, 168 194, 256 88 Z` (hauteur 336, largeur 176, rapport 1 : 1,9). Dégradé vertical `#FFFFFF → #DCE7EC` sur fond sombre, ombre douce `0 18px 34px rgba(2,10,16,.55)`. **Jamais de contour, jamais de rotation, jamais d'aplat gris intermédiaire.** (Remplace le monogramme « A taillé » corail sur encre.)

Deux formes, deux usages — l'écran d'accueil impose la pastille :
- **transparente** (`public/icon.svg`, masters dans `src/assets/` et `public/icons/elan-ogive-{ecume,ardoise}.svg`) : splash, écran de connexion, tout fond sombre ;
- **sur pastille ardoise unie** (`public/icons/*.png` + `elan-ogive-plate.svg`) : icônes PWA et favicons. Sur l'écran d'accueil iOS, l'alpha d'une icône est **écrasé en noir** — une icône transparente y apparaîtrait sur un carré noir sale. `icon-512-maskable.png` réduit le motif à 70 % pour survivre au rognage des icônes adaptatives Android.

Références aux icônes à garder synchronisées si les chemins bougent : `index.html` (favicons + apple-touch-icon + `theme-color`), `vite.config.ts` (manifest), `src/sw.ts` (icône et badge des notifications).

Seul le **nom affiché** a changé (manifest, titre, écran de connexion, splash, notifications, docs). Les identifiants techniques restent en `elan-` **exprès**, parce qu'ils sont persistés ou déployés — les renommer casserait des données ou des URL :

- clés localStorage `elan-data-v1`, `elan-seeded-*`, `elan-mig-subtypes-*`, `elan-plan-anchor-*`, `elan-rappel-*`, `elan-strava-last` → renommer = données locales perdues ;
- `planRef` des séances du plan (`elan-{date}`, `src/lib/planDay.ts`) → **écrit dans les logs Firestore existants**, c'est lui qui dit qu'une séance est validée ;
- `external_id` `elan-` des séances poussées sur intervals.icu (le `--clear` s'en sert pour retrouver les nôtres) ;
- Workers déployés `elan-notif` / `strava-elan` et leurs secrets `ELAN_NOTIF_KEY` / `ELAN_SYNC_KEY`, plus l'URL `strava-elan.saintilan.workers.dev` déjà dans le `.env`.

Les fichiers d'icônes livrés avec la charte gardent eux aussi le préfixe `elan-` (`elan-ogive-*.svg/png`) : c'est le nom du système design d'origine, pas une régression du renommage.

## Architecture

- **Double mode de stockage** (`src/data/store.ts`) : interface `Store` avec `LocalStore` (localStorage, par défaut sans `.env`) et `FirestoreStore` (`users/{uid}/exercises|sessions|logs|ideas`). Le mode est choisi dans `src/firebase.ts` selon la présence des variables `VITE_FIREBASE_*` dans `.env`. La collection `ideas` (bugs & idées saisis dans Réglages) ne bloque jamais `dataReady` et dégrade en liste vide si les règles Firestore la refusent.
- `src/data/DataContext.tsx` : provider unique (auth Google + abonnements aux 4 collections + CRUD + seed au premier lancement via `src/data/seed.ts`, gardé par un flag localStorage `elan-seeded-*`).
- Types et métadonnées de catégories (couleurs/emoji/classes Tailwind) : `src/types.ts`.
- Jours de semaine indexés **0 = lundi … 6 = dimanche** (`src/lib/dates.ts`), dates de logs en `YYYY-MM-DD` local.
- Planification : jours fixes (`Session.days`) OU intervalle (`Session.repeat`). En intervalle, **deux cadences** : « tous les X jours » (`repeat.everyDays` + `repeat.startDate`) OU **sur des jours de semaine choisis** (`repeat.onDays: number[]`, 0=lun…6=dim ; si défini et non vide, `everyDays` est ignoré). La rotation est `repeat.steps: { ids: string[] }[]` : chaque étape regroupe les séances d'un MÊME jour (ex. [Pompes+Abdos] puis [Jambes+Dos]), `occurrence % steps.length` choisit l'étape. **Calcul de l'occurrence** (`plannedSessionIdsOn`, `src/lib/schedule.ts`) : cadence « tous les X jours » → `occurrence = diffDays(startDate, date) / everyDays` (si multiple) ; cadence `onDays` → si `date` un de ces jours de semaine et ≥ `startDate`, `occurrence = countWeekdays(startDate, date, onDays)` (nb de ces jours déjà passés), ce qui pose l'alternance UNIQUEMENT sur les jours choisis (ex. lun/jeu/sam pour éviter les jours de course du plan) tout en la faisant continuer d'une semaine à l'autre. UI : sous-segment « Tous les X jours / Jours de semaine » dans `SessionForm` (états `intervalKind`/`onDays`) ; `applySchedule` écrit `onDays` dans le `repeat` du propriétaire (et le préserve quand on quitte/répare un cycle) ; `describeSchedule` affiche « Lun · Jeu · Sam » (tableau d'objets car Firestore refuse les tableaux imbriqués ; les anciens champs `alternates`/`alternateWith` sont normalisés par `cycleStepsOf()`). Le cycle est porté par UNE séance « propriétaire » ; les membres se détectent via `ownerOf()` et l'éditent depuis leur fiche (réécriture du propriétaire dans `SessionForm.applySchedule`, qui nettoie aussi `repeat` ET `days` des membres et répare les anciens cycles « bidirectionnels »). À la lecture, `canonicalCycles()` (`src/lib/schedule.ts`) garantit qu'une séance n'appartient qu'à un seul cycle (premier propriétaire gagne) et les jours fixes des membres sont ignorés. `repeat: null` / `objective: null` / `goal: null` (et non undefined) pour désactiver — Firestore ne supprime pas les champs absents d'un update.
- Objectifs **à paliers avec récompenses** : `Exercise.goal.levels[]` (meilleure série/volume muscu) et `Session.objective.levels[]` (chaque palier = cibles multi-mesures à remplir dans une même séance + `reward`). Normalisés par `goalLevels()` / `objectiveLevels()` dans lib/metrics (gèrent les anciens formats `value`/`targets`). Gérés dans l'onglet `/goals` (création, modification ✎, suppression), célébrés à la complétion (CompleteSheet) **uniquement pour les paliers nouvellement franchis** (la récompense ne se débloque qu'une fois).
- **Sélecteurs partagés Aujourd'hui ↔ Planning** (`src/lib/planDay.ts` + `src/lib/planningLayout.ts` + `src/lib/usePlanAnchor.ts`, refactor « audit P1 » juin 2026) : la logique « séance du plan due / faite ce jour » et l'ordre des sections étaient dupliqués dans les deux pages et avaient divergé. Désormais source unique : `planWeekFor(date)` (semaine du plan alignée par lundi), `planWeekStates(week, logs)` / `planToDoOn(date, logs)` (état de chaque séance), et `planningSections(ordered, planActive, planAnchor)` (ordre vertical des sections + injection de la section « Running » du plan). **`done` corrigé** : une séance du plan est « faite » si un log porte son `planRef` (validation explicite) OU s'il existe une course **libre** (running SANS `planRef`) le jour prévu — on n'inclut PLUS « n'importe quelle course ce jour-là », sinon la validation d'une AUTRE séance déplacée sur ce jour faisait passer une séance non faite en « faite » (faux positif Planning) ou la masquait de la to-do (faux négatif Aujourd'hui). `usePlanAnchor(uid)` partage l'ancre de la section plan (lecture seule sur Aujourd'hui pour respecter l'ordre du Planning). **Perf** : `canonicalCycles(sessions)` mémoïsé une fois par page et passé en paramètre optionnel à `plannedSessionIdsOn` / `ownerOf` / `describeSchedule` (au lieu d'une reconstruction par jour ET par ligne). **Décomposition du conteneur Planning** (audit P2) : `usePlanningWeek(weekOffset, logs)` (`src/lib/usePlanningWeek.ts` : dates de la semaine, alignement de la semaine du plan, `planStates`, indice de démarrage) et `usePlanningOrdering({ sessions, planActive, planAnchor, savePlanAnchor, updateSession })` (`src/lib/usePlanningOrdering.ts` : ordre optimiste `orderIds`, `planningSections`, sensors + `handleDragEnd` sections/séances) ; `Planning.tsx` ne garde que la grille (cycles/plannedByDay/doneByDay/perWeek), `validateDay` et le rendu. **Identité des logs du plan** (audit P2) : `isPlanLog(l)` = `!!l.planRef` est LE discriminant (le `sessionId: ''` posé à la création dans WorkoutSheet est une convention à ne pas tester) ; `doneIds` (Aujourd'hui) et `doneByDay` (Planning) excluent les logs du plan, et le compteur d'en-tête « N séances/sem. » ajoute `planStates.length` (les courses du plan de la semaine, longtemps oubliées du total).
- L'écran Aujourd'hui navigue dans les dates passées (saisie rétroactive) **ET futures** (aperçu des jours à venir : libellé d'en-tête `isToday ? Aujourd'hui : isFuture ? À venir : Saisie passée`, état vide futur « journée repos ») : `CompleteSheet` accepte une prop `date`. **Le jour affiché est un OFFSET relatif** (`dayOffset`, et non une date figée au montage) → la vue suit le passage de minuit ; un écouteur `visibilitychange`/`focus` force le recalcul au retour sur l'onglet (audit P3). **Sur une date future, `CompleteSheet` est en aperçu seul** : programme visible mais aucun bouton de saisie/validation (« Séance à venir — reviens le jour J ») — on ne journalise pas l'avenir (audit P3). **Il injecte aussi les séances de course du plan semi** dues le jour affiché (via `planToDoOn`), en carte à-faire typée `TYPE_META` (icône `Footprints`) qui ouvre le `WorkoutSheet` (consulter + « Valider ma séance ») — exactement comme le Planning. Une séance déjà faite (cf. `done` ci-dessus) quitte la to-do (son log s'affiche dans « Terminées »). **L'ordre des cartes du jour suit EXACTEMENT le Planning** : on parcourt `planningSections(sessions, …)` et, dans la section « Running », on insère la séance du plan avant les séances utilisateur de la section (avant, Aujourd'hui listait un plat `sortOrder` ignorant les sections → ordre différent du Planning, bug juin 2026).
- Sémantique par sport : running = simple coche ; vélo = formulaire perfs (préremplies depuis le dernier log, programme prévu affiché à l'avance via `MetricDef.target`) ; muscu = séries×reps (exercices `measure: 'sec'` pour le gainage), avec **séries variées** possibles (`SessionItem.targets: number[]`, ex. 30/20/15, normalisé par `setTargetsOf()` dans types.ts qui prime sur `target`) ; HIIT/étirements/muscu = minuteur guidé `src/pages/Player.tsx` (WebAudio + vibration + wake lock ; en muscu les séries en reps s'ajustent en − / + puis « Série faite ✓ », le gainage et les repos sont chronométrés). Le Player journalise le **réalisé réel** (`doneRef`, muscu ET HIIT) : reps ajustées, durée cible si chrono tenu, temps écoulé si « Passer » ≥ 3 s ; séries « **mal réalisées** » marquables pendant la séance — bouton « Série ratée ? » sur l'écran de repos (dernière série, `lastSetRef`) et tap sur une ligne travaillée du tiroir programme (bascule toutes les séries enregistrées de l'exo, ⚠ ambre). - **Rappels de séance par notification push** (juillet 2026) : notification « Séance du jour — Fractionné 6×800m · Gainage » à l'heure choisie (7h30 par défaut), rien les jours de repos ni si la séance est déjà validée ; tap → ouvre l'app. **Jusqu'à 4 rappels par jour** (`MAX_HOURS`, miroir app/Worker) : `entry.hours: string[]` trié, et `entry.lastSent` est un objet **par heure** (`{ '07:30': '2026-07-10' }`) — c'est ce qui laisse partir le rappel de midi alors que celui du matin est déjà parti. Le titre dépend du **rang** de l'heure dans la liste triée (`notificationText(names, rank)`) : rang 0 = « Séance du jour » (annonce), au-delà = « Pas encore fait » (relance) ; un rappel unique posé le soir a donc le rang 0 et annonce, ce qui est correct. Une relance de midi/soir se tait d'elle-même si la séance a été validée entre-temps, puisque l'app réécrit l'agenda à la validation et que le jour en disparaît. Deux heures dont les fenêtres de 15 min se chevauchent → le Worker n'envoie que la plus tardive et marque l'autre (`alsoMark`), jamais deux notifications d'affilée ; l'app refuse de toute façon deux rappels à moins de `MIN_GAP_MIN` (15 min). Rétrocompatibilité : l'ancien champ `hour` (heure unique) et l'ancien `lastSent` (une date) sont normalisés par `hoursOf()` / `lastSentOf()` — la date est rattachée à la première heure, sinon le rappel du matin serait rejoué le jour de la migration. **Une PWA ne peut PAS programmer une notification locale à l'avance** : l'API Notification Triggers (`showTrigger`) a été abandonnée par Google (« No longer pursuing »), jamais activée dans un navigateur stable, et un `setTimeout` dans un service worker ne survit pas à son éviction → **un serveur DOIT envoyer un push**. Chaîne : `usePushReminders` (`src/lib/usePushReminders.ts`, calqué sur `useStravaSync`) demande la permission, s'abonne (`pushManager.subscribe`, `userVisibleOnly: true`) et POSTe au **Worker Cloudflare `elan-notif`** (`worker/notif/`) un **agenda pré-calculé des 30 prochains jours** (`buildAgenda`, `src/lib/reminderAgenda.ts`) ; un **Cron Trigger** `*/5 * * * *` réveille le Worker, qui convertit l'instant courant dans le fuseau de l'abonné (`Intl.DateTimeFormat` → le passage heure d'été/hiver se gère seul, le cron étant en UTC) et pousse le rappel (`web-push-browser`, VAPID ES256 + `aes128gcm` RFC 8291). **Le Worker ne calcule JAMAIS le planning** : `buildAgenda` réutilise `canonicalCycles`/`plannedSessionIdsOn`/`planToDoOn` (mêmes fonctions qu'Aujourd'hui, `doneIds` excluant les logs `planRef` à l'identique) — le réimplémenter côté serveur créerait une seconde source de vérité vouée à diverger. Conséquence assumée : **l'agenda périme** (app pas ouverte pendant > 30 j → rappels arrêtés, repartent à la réouverture). **Identité = SHA-256 de l'endpoint push** (clé KV), pas l'`uid` Firebase : l'endpoint est une URL non devinable et EST la capacité que l'entrée protège → pas de JWT à vérifier, rappels disponibles en mode local, une entrée (donc un rappel) par appareil. `ELAN_NOTIF_KEY` en `Bearer` = anti-abus léger seulement (clé embarquée dans le bundle, donc publique), comme le Worker Strava. Le **service worker est écrit à la main** (`src/sw.ts`, stratégie `injectManifest` dans `vite.config.ts`) : il reproduit l'`autoUpdate` (`skipWaiting`/`clientsClaim`) et ajoute `push` + `notificationclick`. Typé à part (`tsconfig.worker.json`, `lib: ["WebWorker"]` incompatible avec le `DOM` de `tsconfig.app.json`, qui l'exclut). Anti-gaspillage KV : l'app ne renvoie l'agenda que si `agendaFingerprint` a changé (plan gratuit = **1 000 écritures KV/jour**). UI : bloc « Rappels de séance » des Réglages (icône Lucide `Bell`, même moule `rounded-2xl bg-sage-50 p-4` que « Courses Strava »), masqué si `VITE_NOTIF_URL` absent.

## Pièges connus

- Firestore refuse `undefined` → tout passe par `clean()` dans store.ts ; les champs optionnels vidés sont stockés comme `''`.
- `tsconfig` strict avec `noUnusedLocals` : tout import non utilisé casse le build.
- **Les CSS de `@fontsource` s'importent SANS l'extension `.css`** (`'@fontsource/space-mono/latin-400'`). Leur champ `exports` mappe `./*` vers `./*.css` : écrire l'extension demande `latin-400.css.css` et **le build vite/rolldown échoue** (« failed to resolve import »). TypeScript, lui, refuse alors l'import d'effet de bord (TS2882) — d'où le `declare module '@fontsource/*'` dans `src/vite-env.d.ts`. Les anciens imports Nunito gardent leur `.css` parce qu'ils résolvent déjà, ne pas les « harmoniser » sans revérifier le build.
- Le bundle dépasse 500 kB (Firebase + Recharts) : avertissement vite normal.
- **Tout push DOIT afficher une notification.** Chrome impose `userVisibleOnly: true` et sanctionne les pushs muets : il affiche « Ce site a été mis à jour en arrière-plan », puis **révoque l'abonnement**. D'où : pas de séance aujourd'hui → le Worker n'envoie rien du tout, et `src/sw.ts` affiche un message de repli si la charge utile est illisible.
- **Sur Android, installer Avel sur l'écran d'accueil.** Pas requis pour recevoir les pushs (contrairement à iOS), mais depuis fin 2025 Chrome désabonne d'office les sites peu consultés qui notifient beaucoup — **les PWA installées en sont exemptées**.
- **Web Push depuis un Worker** : le paquet npm `web-push` ne marche PAS sur Cloudflare Workers, même avec `nodejs_compat` (il appelle `crypto.createECDH` et `https.request`). `@pushforge/builder` et `@block65/webcrypto-web-push` codent en dur l'ancien `aesgcm` (draft-04, déprécié, jamais supporté par Safari). Seul **`web-push-browser`** fait `aes128gcm` (RFC 8291) — et son option `algorithm` est **obligatoire** malgré sa doc (« defaults to AES128GCM »), sans quoi `createCEKInfo` lève « Invalid algorithm ».
- **Clé privée VAPID au format PKCS8**, pas le scalaire `d` brut : `deserializeVapidKeys` fait `importKey('pkcs8', …)`. La clé publique, elle, est au format RAW (65 octets, préfixe `0x04`) — c'est aussi l'`applicationServerKey` du navigateur.
- Régénérer les clés VAPID **invalide tous les abonnements existants** ; `scripts/generate-vapid.mjs` refuse donc d'écraser des clés présentes dans `.env`.
